Across my automation projects at WIDO, a recurring piece of work is choosing and wiring together the right no-code/low-code data and interface layer for a client — not just the workflow engine, but where the data lives and how people interact with it.

## Context

Clients typically needed one of the following, without the budget or need for a custom-built backend:

- a lightweight, structured database their own team could edit
- an internal knowledge base or process reference
- a public-facing form to collect leads or requests

## Problem

Meeting these needs without a dedicated developer on the client side made it hard to:

- **store structured data** without building or maintaining a custom database
- **keep a single source of truth** for process knowledge that was otherwise scattered or nonexistent
- **avoid manual re-entry** between public-facing intake and the automated backend

## My Role

Selecting, configuring, and integrating the no-code/low-code data and interface tools for each project, and making sure they connect reliably to the automations and AI agents built on top of them.

## Problems Encountered

- Clients needed structured data storage without a dedicated developer to maintain a custom database.
- Internal documentation and process knowledge was scattered or nonexistent, making it hard for automations to reference a single source of truth.
- Public-facing intake needed to be simple to fill out but still feed cleanly into the automated backend, without manual re-entry.

## Solutions Built

**Data layer.** Used Airtable or Supabase as the structured data layer depending on the project's complexity — Airtable for lighter, client-editable datasets; Supabase when the project needed a real relational database with API access.

**Documentation hub.** Set up Notion as the shared documentation and process hub so both the client team and the automations had one reference point for how a workflow was supposed to behave.

**Intake.** Built intake forms with Jotform, Tally, or Fillout that fed directly into the automation pipeline via webhook, removing manual re-entry between form submission and CRM/database update.

**Backend logic.** Used Xano where a project needed backend logic and an API layer beyond what Airtable/Supabase offered natively.

## Business Value Delivered

- **A maintainable data layer** — clients can view and adjust their own data without a developer.
- **One source of truth** — process documentation and automation logic reference the same place.
- **No manual re-entry** — form submissions flow straight into the client's systems of record.
- **Room to scale** — Xano available as a fallback when a project outgrows what no-code databases can handle.

## Technical Stack & Why Each Tool Was Selected

- **Airtable** — chosen for lightweight, client-editable datasets where a spreadsheet-like interface lowers the barrier for non-technical teams to view and adjust their own data.
- **Supabase** — used instead of Airtable when the project needed a real relational database with proper API access and scale beyond what a spreadsheet-style tool supports.
- **Notion** — selected as the documentation hub because it's flexible enough to hold both process documentation and lightweight databases in one place the client's team already understood.
- **Xano** — brought in specifically when a project needed custom backend logic and an API layer that no-code database tools alone couldn't provide.
- **Jotform / Tally / Fillout** — chosen for public-facing intake because they support direct webhook integration, letting form submissions flow straight into the automation pipeline instead of needing manual transcription.
