As a freelance Technico-Functional Consultant at Disneyland Paris, I was the cross-functional technical project lead and application support reference for a CMS platform used simultaneously by Disney's Europe, Americas, and Asia entities.

## Context

The CMS wasn't a single-team tool — it was shared infrastructure across regional entities with different priorities, release calendars, and stakeholders. Any change had to account for Run (keeping the platform stable for everyone currently using it) and Build (shipping new functionality) at the same time, across time zones and organizations.

## My Role

I piloted both Run and Build for the platform: gathering requirements from different regional stakeholders, translating them into functional specifications and User Stories, coordinating across Product, Design, IT, and QA teams, and owning migration planning and risk analysis for platform changes.

## Problems Encountered

- Requirements from different regional entities sometimes conflicted, and there was no single backlog reconciling them.
- Cross-team coordination was fragmented — Product, Design, IT, and QA each had their own view of priorities and status.
- Releases and migrations carried real risk: a platform issue affected multiple regions simultaneously, so changes couldn't be shipped without a clear rollback and risk plan.
- Governance and change history were not consistently documented, making it hard to trace why a decision was made after the fact.

## Solutions Built

- Ran structured requirements-gathering sessions with each regional stakeholder group and consolidated them into functional specs and User Stories in a single governed backlog.
- Set up and ran Agile/Scrum ceremonies (planning, backlog grooming, reviews) to keep Product/Design/IT/QA aligned on the same priorities and delivery calendar.
- Built migration plans with explicit risk analysis before any platform-level change, including rollback steps.
- Documented decisions and process changes to support governance and give the client's teams a clear change history to work from.

## Results

The platform maintained stable Run operations for all three regions while Build work continued in parallel, with releases and migrations delivered against a documented, risk-assessed plan instead of ad hoc coordination.

## Technical Stack & Why Each Tool Was Selected

- **JIRA** — chosen as the single backlog and issue tracker so every region's requirements and every team's tasks lived in one place instead of scattered spreadsheets and email threads.
- **Confluence** — used for functional specs, migration plans, and governance documentation, since decisions needed to be traceable well after the sprint that made them.
- **Agile/Scrum ceremonies** — the delivery framework chosen specifically because it gave recurring checkpoints (planning, review) where conflicting regional priorities could surface and get resolved early, rather than at release time.
